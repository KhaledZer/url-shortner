URL Shortener — A Two-Developer Build Plan

A 13-phase, step-by-step roadmap for two beginner developers to ship the URL shortener from the design. Both developers write backend AND frontend code. Each owns a feature that spans the whole stack, so by the end you'll have both built REST endpoints in NestJS and React pages in Next.js. Tasks at the end of every phase tick off as you go and persist in your browser.

Pace: ~8–10 weeks part-time Prerequisites: none — really Output: a deployed app, a portfolio repo, a real teammate

What you are building & how the work splits

A user pastes a long URL → the system returns a short one. When anyone visits that short URL → the system redirects them. Click counts power a small dashboard. You'll build it in 13 phases, growing into the design as your skills grow.

User─POST─▶ Next.js─POST─▶ NestJS API─INSERT─▶ Postgres
Anyone─GET /slug─▶ NestJS API─lookup─▶ Cache → DB─302─▶ Original URL

Phase 0 Both Devs · Pair

Foundations — Tools, Accounts, First Commit

Goal: both machines are ready. Both names appear in the same Git history. You've made a commit, pushed it, and pulled the other person's.

The big picture

Before any project code, you need the rails everything else runs on: Node.js, a package manager, an editor, Git, GitHub, and the muscle memory of making a commit. Take this phase slowly. Most pair projects silently fail in week three because someone's on a different Node version or never set up SSH keys.

What is Node.js?

A browser runs JavaScript. Node.js lets you run JavaScript anywhere else — on your laptop, on a server. Both NestJS and Next.js are programs that run on Node.js. Install the version labelled LTS (Long-Term Support) and confirm you both have the same major version (the number before the first dot).

What is a package manager?

Your project will pull in hundreds of small libraries written by other people. A package manager downloads them, records exact versions in a package.json, and locks them so the next dev gets the same set. npm ships with Node.js; pnpm is faster and more disk-friendly. Pick one. Stay consistent.

What is package.json? What's a lockfile?

package.json is your project's name card: the project name, scripts you can run (npm run dev, npm run build), and the libraries you depend on with version ranges. The lockfile (package-lock.json or pnpm-lock.yaml) records the exact version of every direct AND indirect dependency, so installs are reproducible. Both files are committed to Git. Never hand-edit the lockfile.

Library vs Framework — what's the difference?

A library is code you call from your code (you're in charge). A framework calls your code at the right times (it's in charge — "Hollywood principle: don't call us, we'll call you"). React is mostly a library. NestJS is a framework. Next.js is a framework. Frameworks give beginners structure; libraries give you flexibility.

What is Git?

A time machine for your code. Every "commit" is a snapshot with a message. You can rewind, branch off into experiments, and merge back. It works locally — no internet required — until you sync with a remote.

What is GitHub?

A website that hosts Git repositories and adds collaboration features: pull requests, code review, issues, automated checks. Git is the tool. GitHub is one place that uses it. (GitLab and Bitbucket are alternatives.)

Four Git words — repository, commit, branch, remote

  • Repository (repo): a folder Git is tracking.
  • Commit: a saved snapshot + a message.
  • Branch: a parallel line of commits. main is the default.
  • Remote: a copy of the repo somewhere else. origin is the default name for "the one on GitHub."

Dev A — Setup & the API repo

  • Install Node.js LTS. Verify with node -v.
  • Install pnpm (or stick with npm) and verify the version.
  • Install VS Code (or the editor of your choice).
  • Install Git. Run git config --global user.name and user.email so commits are attributed to you.
  • Create a GitHub account if you need one. Add an SSH key (search "GitHub SSH key setup").
  • Create the repo url-shortener-api. Add Dev B as a collaborator. Initialize it with a README and a Node-flavored .gitignore.

Dev B — Setup & the Web repo

  • Install Node.js LTS — same major version as Dev A.
  • Install pnpm (or npm) — match Dev A.
  • Install VS Code or your editor.
  • Install Git. Configure user.name and user.email.
  • Create a GitHub account if needed. Add an SSH key.
  • Create the repo url-shortener-web. Add Dev A as collaborator. README + Node .gitignore.

First pair session — sit together or share a screen

  1. Both clone both repos.
  2. Write a one-paragraph README in each repo: what the project is, who you both are, which stack lives there.
  3. Each dev pushes a commit to their own repo.
  4. Each dev pushes a second commit to the other dev's repo (a typo fix in the README is enough). Goal: both names appear in both histories on day one.

Your starter Git vocabulary

  • git status — your best friend; ask it constantly.
  • git add <file> — stages a change for the next commit.
  • git commit -m "..." — saves a snapshot.
  • git push — sends commits to GitHub.
  • git pull — fetches and merges from GitHub.

Hints

  • Use a curated .gitignore template — search "Node gitignore template" and copy the standard one. It'll save you committing 80,000 node_modules files.
  • Make your first commit tiny so you feel the whole cycle: edit → save → add → commit → push → refresh GitHub → see it.
  • If a Git command outputs more than three lines, read all of them. Git is unusually clear about what to do next.
  • SSH key setup is annoying once. Worth it. Don't skip it for HTTPS — you'll thank yourself in Phase 11.

Common day-one traps

  • Mismatched Node versions silently break things in week 3. Verify with node -v.
  • Committing node_modules. Use a .gitignore before your first npm install.
  • Two people pushing to main simultaneously. Branches start in Phase 2.

Phase 1 Both Devs · Pair

Read the Map — Understand the Design

Goal: both devs can narrate every flow without notes and have written down the API contract together.

The big picture

Code is downstream of understanding. Sit with the Excalidraw design, finger-trace each path, and write down what you see. If you can't tell the story aloud, you're not ready to build it.

Client and server

The client asks. The server answers. Your browser is the client; your NestJS process is the server. The labels are about direction, not location.

What is an API?

A contract: "send me a request shaped like this, I'll send you a response shaped like that." For this project the API is the set of URLs your NestJS backend answers. Your Next.js frontend is one client of it; curl and Postman are other clients.

HTTP — the language of the web

Every HTTP request has four parts: a method (GET, POST…), a URL, headers (metadata: who you are, what you accept), and an optional body. The response has a status code, headers, and a body.

HTTP methods — the verbs

  • GET — "give me something." No body. Safe to repeat.
  • POST — "create something new." Has a body. Not safe to blindly repeat.
  • PUT / PATCH — "update."
  • DELETE — "remove."

Status codes — the answer's mood

  • 2xx — success (200 OK, 201 Created).
  • 3xx — redirect (301 permanent, 302 temporary).
  • 4xx — you messed up (400 Bad Request, 404 Not Found).
  • 5xx — the server messed up.

What is REST?

An informal style for designing APIs where each URL points to a resource (a thing — a link, a user, a click event) and HTTP methods express what you're doing to it. GET /links lists links; POST /links creates one. You're building a REST-ish API in this project.

Pair exercise — paper before code

Open the Excalidraw diagram and a blank document. Together, write:

  1. API contract. One row per endpoint: method, path, purpose, request body, response shape, status codes. Example: POST /links — create a short link · body: { originalUrl } · 201 returns { slug, originalUrl, createdAt }.
  2. Page list. One row per frontend page: route, purpose, what data it needs.
  3. Happy path narratives. "Create a link" and "Use a link" in plain English, naming every hop.
  4. Ownership table. For each endpoint and each page, write the owner: A or B. Use the table in the Overview as a starting point and customise.

Commit this document to both repos under docs/api.md.

Hints

  • Open the Network tab in your browser on a site you use every day. Watch real HTTP requests flow. Names of headers will start to look familiar.
  • Don't try to design auth, admin permissions, custom domains, or expiring links yet. V1 endpoints number three or four total.
  • If you struggle to narrate a flow, draw stick figures and arrows on paper. Engineers do this on real whiteboards every day.
  • Names are hard. Argue about them now, before writing code, not after.

Scaffold — Both Apps Live

Goal: a running NestJS server and a running Next.js dev server. Both committed via a PR.

The big picture

"Scaffolding" means generating the project skeleton from a template so you don't have to wire everything by hand. Both NestJS and Next.js ship with a CLI that does this. Today you run them, push the result, and confirm the apps boot. No features yet.

What is NestJS?

A TypeScript framework for the backend. It enforces a structure of modules, controllers, and services, ships with tools for testing, dependency injection, validation, and more. It runs on top of either Express or Fastify under the hood — you don't usually care which.

What is Next.js?

A React framework for the frontend. It adds file-based routing, server-side rendering, automatic code-splitting, and a slick dev experience to plain React. The current default routing system is the App Router (the app/ folder). Use that — the older pages/ system is legacy.

What is a port?

A computer runs many services at once. Ports are numbered slots — :3000, :5432 — that distinguish them. NestJS defaults to 3000, Next.js defaults to 3000. They will fight. Change one to 3001.

What is hot reload / fast refresh?

Save a file → the browser updates instantly. No restart. This is a dev-mode trick both frameworks give you. Notice it. Appreciate it. Then remember production builds work differently.

What is ESLint? What is Prettier?

ESLint is a linter — it scans your code for likely mistakes and bad patterns and warns you. Prettier is a formatter — it rewrites your code in a consistent style so you stop arguing about indentation. Both come pre-configured in the scaffolds. Use them on save in your editor; they'll save more time than they cost.

Dev A — Scaffold NestJS be

  • Install the Nest CLI globally. Look it up — the binary is named nest.
  • Inside url-shortener-api, scaffold a new NestJS project into the repo root.
  • Change the listening port to 3001 (NOT 3000 — Next.js will want 3000).
  • Run the dev server. Visit it. Read what the default response says.
  • Open a branch chore/initial-scaffold. Commit. Push. Open a PR.

Dev B — Scaffold Next.js fe

  • Run the Next.js scaffolding command. Pick: TypeScript: yes, ESLint: yes, Tailwind: yes, App Router: yes. Take defaults for the rest.
  • Run npm run dev. Visit the printed URL.
  • Open app/page.tsx and change the heading text. Watch hot refresh.
  • Branch chore/initial-scaffold. Commit. Push. Open a PR.

Git Moment — Branches, PRs, and Conventional Commits

From now on, nobody pushes to main directly. Every change lives on a branch, gets a Pull Request, gets reviewed, gets merged.

  • git switch -c feat/something creates and moves to a branch.
  • Push the branch: git push -u origin feat/something.
  • On GitHub, click "Open pull request." Title is what changed; body explains why.
  • Use the merge strategy "Squash and merge" — cleanest history for beginners.

Conventional Commits: a small convention where every commit message starts with a type, like: feat: add health endpoint, fix: handle empty slug, chore: bump dependencies, docs: update README. Adopt it from day one. It makes scanning the history a joy.

Pair time — swap reviews

Dev B reviews the backend PR. Dev A reviews the frontend PR. You're not expected to deeply understand the other stack — review for names, README clarity, presence of .gitignore, whether the commands documented in the README actually run.

Hints

  • The first time the framework boots, it'll print a URL. Click it. Don't change anything else first.
  • NestJS asks which package manager during scaffolding. Pick the one you have installed.
  • Next.js gives you a lot of files. Don't panic. app/page.tsx and app/layout.tsx are the ones you edit.
  • Add a "How to run locally" section to each README. Future-you will thank present-you.
  • Enable "Format on save" in VS Code so Prettier runs automatically.

Gotchas

  • Forgetting to change the NestJS port. Both servers will scramble for 3000.
  • Committing node_modules. Check your .gitignore before first install.
  • Editing the lockfile by hand. Don't.

Hello, Stack — First Endpoint & First Page (you do both)

Goal: each dev writes a real endpoint in the backend AND a real page in the frontend. Both stacks, both devs, this phase.

The big picture

You will each write a primary piece (your own stack) and a secondary piece (the other stack). The crossover is small but real — you'll touch the folder structure and feel the rhythm of the other framework so nothing feels foreign later.

What is a controller? (NestJS)

A class that catches HTTP requests and routes them to the right handler methods. You tell NestJS which URLs it cares about using decorators — labels prefixed with @. @Controller('links') means "this class handles URLs under /links"; @Get('health') means "this method handles GET /links/health".

What is a service? (NestJS)

A class that holds the actual business logic — generating a slug, querying the DB, talking to the cache. Controllers are thin (accept the request, call a service). Services are fat (do the work). This separation makes both easier to test and reuse.

What is a module? (NestJS)

A bundle of related controllers and services declared as a unit. Your app will have a LinksModule with a controller and a service inside it. Modules can import each other to share things.

What is a decorator?

A function call you prefix with @ that attaches metadata to a class, method, or parameter. NestJS uses them everywhere: @Controller, @Get, @Body, @Injectable. Don't worry about how they work internally — focus on reading them.

Route vs endpoint — same thing?

Close enough. A route is the path pattern (/links/:id). An endpoint is the combination of method + route (GET /links/:id). People use them interchangeably; pick one and roll with it.

What is a React component?

A function that returns JSX. Reusable. Names always start with a capital letter — that's how React knows to render your component vs an HTML tag.

What are props?

Props (short for "properties") are the inputs a component receives, written like HTML attributes. <Greeting name="Sam" /> passes name as a prop. Inside the component function, you receive an object: function Greeting({ name }) { ... }. Props are read-only — the parent owns them.

What is JSX, really?

HTML-shaped syntax that lives inside JavaScript. The browser doesn't understand it directly; a build tool converts it to plain JS function calls. Rules: write className not class, close every tag, and return one root element (wrap siblings in <>...</>).

What is TypeScript?

JavaScript with types. You annotate that slug is a string; the editor catches your mistakes before you run anything. A small effort up front saves whole evenings of debugging. Both NestJS and Next.js use it by default.

The App Router file structure (Next.js)

Inside app/, folders become URL segments. A file called page.tsx in a folder is the page served at that path. app/page.tsx is /. app/about/page.tsx is /about. layout.tsx wraps every page in that folder.

Phase 4 Pair · Both stacks

The Handshake — Frontend Talks to Backend

Goal: the homepage shows data fetched from your backend. CORS is configured and understood. Both devs touch both repos in this phase.

The big picture

Two apps. Two ports. One must call the other. This is your first real "the system fights back" moment — you'll hit a CORS error. That's good. You'll learn more from this 45-minute roadblock than from a week of tutorials.

What is fetch?

A function built into the browser (and modern Node) that sends an HTTP request and returns a Promise. You call it with a URL, optionally a method, headers, and body. Most modern HTTP code starts with fetch.

What is a Promise?

A value that will exist later. Network requests take time; the function returns a placeholder you can attach handlers to. A Promise has three states: pending → either fulfilled or rejected. Once settled, it never changes.

What is async / await?

Friendly syntax for Promises. Write const r = await fetch(...) and JavaScript pauses on that line until the Promise resolves. The function containing the await must itself be marked async. Use try/catch to handle rejections.

What is JSON?

A text format for objects: keys and values wrapped in braces. It's the lingua franca of APIs. Backend sends it; frontend parses it with .json(). Strings are quoted, numbers aren't, no trailing commas. Note: .json() is itself async — two awaits, not one.

What is CORS — and why is it yelling at you?

"Cross-Origin Resource Sharing." Your frontend lives at localhost:3000; your backend at localhost:3001. Different origins. Browsers refuse by default to let one origin call another, for security reasons. Fix: the backend must explicitly say "I accept requests from that origin." NestJS exposes a single function for this.

What is an environment variable?

A value loaded from outside the code — typically a .env file or the OS. Examples: database password, API URL, secret keys. Secrets stay out of Git; values that differ between local and production are easy to switch. In Next.js, NEXT_PUBLIC_* vars are exposed to the browser; everything else stays server-only.

Server component vs Client component (Next.js)

In the App Router, components are server components by default: they render on the server, ship no JS to the user. If a component uses state (useState), event handlers (onClick), or browser APIs, it must be a client component. You opt in by writing 'use client' as the first line of the file.

Dev A — Backend CORS & env be

  • Enable CORS in your NestJS app. Look up app.enableCors.
  • Read the allowed origin from an env var, not a literal string. Default to http://localhost:3000 for dev.
  • Create a .env.example (no real secrets) and document expected variables.
  • Confirm .env is in .gitignore.

Dev B — Ping button on the frontend fe

  • Build a small client component with a "Ping API" button.
  • On click, fetch /links/health and display the response.
  • Show loading and error states explicitly.
  • Read API base URL from NEXT_PUBLIC_API_URL. Add a .env.example.

Pair time — fail then succeed, together

Do this side by side. Open the dev tools Network tab before clicking the button. Watch the request fail with a CORS error. Read the message out loud. Fix it. Click again. Celebrate when "Ping API" returns the health JSON.

Gotchas

  • Forgetting 'use client' in a component that uses useState — the error is loud but easy to skim past.
  • Only NEXT_PUBLIC_-prefixed env vars reach the browser. Everything else is server-only by design.
  • Committing .env. Never. Use .env.example with placeholder values.
  • Awaiting fetch but forgetting to await .json() — you'll log a Promise instead of the data.

Hints

  • Don't write a clever "API client" abstraction yet. A single inline fetch is fine.
  • If your spinner blinks too fast to see, add a deliberate delay while developing — then remove it before merging.
  • If a CORS error is unclear, read it word-for-word. The browser literally states which origin it expected.

Phase 5 Pair · Backend-heavy

Memory — The Database

Goal: Postgres runs locally, a Link table exists, queryable from NestJS via Prisma. Both devs participate.

The big picture

Until now, nothing has been saved. Restart the server, data is gone. A database fixes that. Both devs sit together on this one — every full-stack developer needs to read a schema and run a migration without panic.

What is a database?

A program whose only job is to store data and answer questions about it reliably. It survives restarts, handles concurrent users, and gives you a query language.

SQL vs NoSQL — one sentence each

SQL (relational): data lives in tables with a strict schema; rows can reference each other by ID. PostgreSQL, MySQL. NoSQL: looser shape, often tuned for one access pattern. MongoDB, Redis. For your canonical Link table, relational is the right choice.

Schema. Primary key. Unique constraint.

A schema describes the shape of your tables. A primary key uniquely identifies a row — usually a number or a UUID. A unique constraint on a column enforces that no two rows share a value there (your slug column needs this).

What is an ORM? Why Prisma?

An ORM (Object-Relational Mapper) lets you read/write the database with typed objects instead of raw SQL strings. Prisma is the most beginner-friendly choice for TypeScript projects: you write a schema file, Prisma generates a typed client and the migration files.

What is a migration?

A version-controlled change to your database schema. Add a column → write a migration. Migrations are committed to Git so every dev (and production) replays them in the same order. Never edit a migration that's been merged. Add a new one instead.

What is a connection string?

A single URL-like string that tells your app how to reach the DB: postgres://user:password@host:port/dbname. It lives in .env, never in Git.

Pair tasks — both pairing throughout

  1. Run Postgres locally. Easiest: a Docker container. Native install is fine on Linux.
  2. Install Prisma in the API repo.
  3. Together, design the Link model on paper first: id (auto), slug (unique string), originalUrl (string), createdAt (timestamp). Discuss every column out loud.
  4. Write the Prisma schema file. Run the first migration. Confirm the table exists with a GUI like TablePlus or DBeaver, or via psql.
  5. Wire a PrismaService into NestJS so other modules can use it.
  6. Commit the migration AND the schema file.

Hints

  • Search "Prisma NestJS recipe" — the official guide saves an hour.
  • Schema first, queries later. Design names you'd be happy seeing in a year.
  • "Why isn't the slug column the primary key?" Good question — think about whether you might change a slug later. Auto-increment IDs are stable identifiers internally; slugs are stable for the world.
  • Use npx prisma studio to browse the DB visually. Wonderful tool for beginners.

Gotchas

  • Connection string typos silently fail. Triple-check user, password, host, port, dbname.
  • Editing a merged migration. Don't. Add a new migration.
  • Docker on Linux exposes ports differently than on Mac/Windows. If the API can't reach the DB, check host/port and platform docs.

Shorten a Link — The Create Flow

Goal: paste a URL → click submit → get a working short link. Dev A writes the backend, Dev B writes the frontend, both touch the contract.

The big picture

This is your first end-to-end feature. Treat it as a small product. Lock the API contract first, work in parallel, integrate at the end.

What is a DTO and why create one?

DTO = Data Transfer Object. A class describing the exact shape of data crossing a boundary — here, the request body coming from the frontend. Three reasons to bother instead of accepting raw bodies:

  1. Validation. Attach rules ("this must be a URL", "max length 2048") and reject bad input before it touches your service.
  2. Documentation. A new developer reads the DTO and knows what to send.
  3. Safety. If the client sends extra fields like isAdmin: true, the DTO simply ignores them.

What is validation?

Checking that incoming data has the shape and content you expect. NestJS pairs with the class-validator library so you annotate DTO fields with decorators like @IsUrl(), @MaxLength(2048), @IsOptional(). A global "validation pipe" then enforces them on every request — garbage in becomes 400 Bad Request, never an unhandled crash.

What is dependency injection? (NestJS)

Instead of a controller doing new LinksService(), NestJS hands one in via the constructor. The framework creates and caches the right instances. Why care? Testing becomes trivial (you swap in fakes); pieces are wired loosely rather than tightly.

Body vs path parameter vs query parameter

  • Body — the payload of a POST/PUT/PATCH. Big, structured. { originalUrl: "..." }.
  • Path parameter — a slot in the URL itself. GET /links/:slug — slug is a path param.
  • Query parameter — appended after ?. GET /links?page=2&limit=20. For filtering, paging, optional flags.

In NestJS: @Body(), @Param(), @Query().

What is a controlled input? (React)

The input's value lives in component state. When the user types, an onChange handler updates state; React re-renders with the new value. "Controlled" because React, not the browser, owns the source of truth.

What is useState?

A React hook — a function call you put at the top of a client component to remember a value between renders. Returns the current value and a setter. Call the setter, the component re-renders with the new value. That's the entire mental model.

Why event.preventDefault()?

When a form is submitted, the browser's default behavior is to reload the page with the form data in the URL. You don't want that. Call event.preventDefault() at the top of your submit handler to stop it.

Use a Link — The Redirect Flow

Goal: visit a short URL → get redirected. The devs swap stacks this phase: Dev B writes the backend redirect, Dev A writes Next.js frontend pieces.

The big picture

The second half of the product. Crucially, the devs swap primary stacks here. Dev B writes their first backend endpoint. Dev A writes their first Next.js page-with-real-thinking. Both feel uncomfortable. Both grow.

What is a path parameter? (NestJS)

A variable piece of a URL. In /abc123, the abc123 is a path param. Declare with @Get(':slug'); read with @Param('slug') slug: string.

301 vs 302 — which redirect to use?

301 Moved Permanently: browsers and search engines may cache the redirect and never call you again. Great for "this URL moved forever."
302 Found (temporary): browsers call you every time. Great for URL shorteners — you want every click to flow through, both to count it and to support changing destinations later.

How does NestJS send a redirect?

Two paths: use the @Redirect() decorator, or grab the response object via @Res() and call its redirect() method. The decorator is simpler; the response-object route gives more control. Pick one, understand the trade-off.

not-found.tsx in Next.js

The App Router has a special file convention: if a folder contains a not-found.tsx, it renders whenever a child route calls notFound() or a path doesn't match. You also place one at the root of app/ as a site-wide 404.

Next.js <Link> vs anchor <a>

Use <Link href="/about"> for internal navigation between Next.js pages — it does client-side routing without a full reload. For external URLs (or for your shortened link, which is served by the API on a different host), a plain <a> tag is correct, often with target="_blank" and rel="noopener noreferrer".

  • Create a new controller at the root prefix (separate from /links). A RedirectController handling GET /:slug is clean.
  • Look up the slug via the Prisma service. If found, send a 302 to originalUrl. If not, throw NotFoundException (NestJS handles it as 404).
  • Test with the browser AND curl -I (just the headers) to confirm the 302 + Location.
  • Reserve common paths — links, version, your health route — so a user-generated slug can't collide with an API route. Discuss with Dev A.

Dev A — Frontend not-found + success enhancements fe

  • Create app/not-found.tsx in the web repo. A friendly "Link not found" page with a button back home.
  • On the homepage's success view from Phase 6, make the short URL a real, clickable <a> tag with target="_blank" and rel="noopener noreferrer".
  • Add a small "Open in new tab" button as well for accessibility.
  • Pair lightly with Dev B for 30 minutes — read their controller, ask one question about how 302s work.

  • Slugs colliding with API routes. If /links is a real route, a user can't have slug links. Decide your policy.

  • Open-redirect security: anyone can submit any URL. For V1 that's the product — but understand the risk.

Speed — Caching

Goal: hot redirects don't touch the database. Dev B continues backend work; Dev A starts the dashboard frontend in parallel.

The big picture

Your design diagram has a cache between the redirection service and the database for a reason. Redirects are read-heavy: the same slug gets clicked thousands of times. Querying Postgres each time is wasteful. Dev B wires in Redis. Meanwhile, Dev A sketches the dashboard frontend that you'll populate with real data in Phase 9.

What is a cache?

A small, fast store that holds copies of frequently-asked-for data. Reads from cache are orders of magnitude faster than reads from a database on disk. The trade-off: a bit of freshness lost in exchange for speed.

What is Redis?

An in-memory key-value store. You SET a key to a value, GET it back by key, optionally with a TTL. It does many other things, but for now treat it as "a very fast dictionary that lives in another process."

Cache-aside pattern

The pattern your design diagram shows. On a read:

  1. Ask the cache by key.
  2. Hit → return the value.
  3. Miss → query the DB, store the result in the cache, then return.

On writes/deletes, you must invalidate the cache to avoid serving stale data. This is famously hard.

What is TTL?

"Time to live." When you set a cache entry, you can attach an expiry — after N seconds, the key is automatically deleted. TTLs are a safety net: even if you forget to invalidate, wrong data won't live forever.

Graceful degradation

If Redis is down, your redirect should still work — just slower (fall through to the DB). The cache is an accelerator, not a hard dependency. Wrap calls in try/catch so a cache failure doesn't crash the request.

Dev B — Redis + cache-aside be

  • Run Redis locally (Docker one-liner).
  • Add a NestJS-friendly cache client. The official Cache Manager is fine for V1.
  • In the redirect service: check Redis first → on miss, query DB and SET with a TTL of ~1 hour.
  • Decide: populate the cache on link creation, or lazy on first read? Discuss the trade-off (and write it down).
  • Log "HIT" or "MISS" for every lookup so you can verify it's working.
  • Cache key naming: namespace it (e.g., link:abc123) to leave room for future caches.
  • Make cache failures non-fatal — graceful degradation.

Dev A — Dashboard layout fe

  • Create a new route at /dashboard (folder + page.tsx).
  • Build the table layout: columns for short URL, original URL, created date, click count (empty for now).
  • Hardcode 3–5 fake rows so the layout is real.
  • Design the empty state: a friendly message + link back to home to create one.
  • Add a header with a "Create new" button (or Link) back to home.
  • Style with Tailwind. Right-align numeric columns. Hover states on rows.

Pair exercise — prove the cache works

Together, hit the same redirect five times. Watch Dev B's logs: first MISS, then four HITs. Then manually update the row in the DB via Prisma Studio to point somewhere else. Hit the redirect again — you'll still go to the old place until the TTL expires or you invalidate. This is what people mean when they say "cache invalidation is hard."

Gotchas

  • Caching the negative case (404 for unknown slugs) — pros (DDOS protection) and cons (a slug created seconds later still 404s). Pick a policy; document it.
  • Forgetting to invalidate on link updates/deletes. Stale data > no data ≠ true; sometimes stale data is worse.
  • Treating Redis as a hard dependency. If Redis dies, your redirects should still work.

Hints

  • Read about cache stampede: what happens when 100 simultaneous requests all miss the cache for the same key? You don't need to solve it in V1, just understand the problem.
  • Long TTLs = more stale data. Short TTLs = more DB hits. Where's the sweet spot for short links? (Hint: links rarely change.)
  • Use the Redis CLI (redis-cli) to inspect keys directly. KEYS * lists everything; GET key reads it.

Insights — Analytics & Dashboard

Goal: every click is tracked; the dashboard shows real numbers. Each dev now writes BOTH backend AND frontend in this phase.

The big picture

This is the phase where both devs do their fullest stack-spanning work. Dev A writes a backend endpoint AND wires the dashboard frontend to it. Dev B writes click-tracking on the backend AND a dynamic stats page on the frontend. By the end of this phase, both of you have written real NestJS endpoints and real Next.js pages.

Why a separate model for clicks?

A successful URL shortener might serve millions of redirects. Each is a small write event with timestamp, user agent, maybe IP. They're written far more often than they're read in aggregate. The design diagram puts them in a document DB (e.g., MongoDB). For V1, a simple Click table in Postgres is perfectly fine — it's a smaller cognitive load. Upgrade later if you ever need to.

Fire and forget / async writes

When someone clicks a short link, the redirect must be fast. Do not make them wait while you write a click event. Trigger the write in the background and don't await it in the redirect handler — but always attach a .catch() so an unhandled promise rejection doesn't crash your Node process.

What is useEffect?

A React hook that runs code after render — for things like data fetching in client components, subscribing to something, or starting a timer. It takes a function and a dependency array; the function reruns when any value in the array changes. For data fetching in Next.js App Router, you should usually prefer server components (no hook needed) and reach for useEffect only when something truly client-side is going on (e.g., real-time updates).

Server vs Client fetching in Next.js

A server component can await fetch(...) directly in its body during render. No useEffect, no loading flicker on initial load — the HTML arrives already populated. Use a client component ('use client' + useEffect or a library like SWR) only when you need interactivity or live updates after mount.

Dynamic route segments (Next.js)

A folder named [slug] in your app/ tree captures any value in that segment. app/links/[slug]/page.tsx serves /links/abc123, with slug = "abc123" available as a prop. This is how you build the per-link stats page.

Pagination — query parameters & DTOs for them too

Once you have many links, you can't return them all. Use query params like ?page=1&limit=20. In NestJS, you can validate query params with a DTO too — sane defaults, max limits.

Robustness — Errors, Tests, CI

Goal: catch your own bugs before users do. Each dev writes tests for their own endpoints and one E2E flow each.

The big picture

You will not test everything. You will test what hurts most when it breaks — the slug generator, the create endpoint contract, and the happy-path end-to-end flow.

Three kinds of tests

  • Unit test — one tiny function in isolation. Fast, narrow. (Slug generator, validation rules.)
  • Integration test — several pieces together. (A controller + service + a real test database.)
  • End-to-end (E2E) test — a real browser clicks through the app like a user. (Create a link, click it, see the redirect.)

What is mocking?

Replacing a real dependency with a fake during a test. Useful when the real thing is slow (network), nondeterministic (random IDs), or has side effects (sending email). Don't mock your own database in integration tests — use a real test DB. Mocks of your own code tend to lie.

CI — Continuous Integration

Automated checks that run on every PR — lint, type-check, tests. A red check blocks merging. GitHub Actions runs these for free. Set it up once, benefit forever.

Dev A — tests for your endpoints + dashboard E2E

  • Unit test for the slug generator: right length, only allowed characters, no duplicates in a batch of N.
  • Integration test for POST /links: valid → 201, invalid URL → 400, empty body → 400, missing field → 400.
  • Integration test for GET /links: returns the right shape, pagination respects limits.
  • Playwright E2E: open the homepage → paste a URL → submit → see the success view with a short URL.
  • Add a GitHub Actions workflow that runs lint + type-check + tests on every PR.

Dev B — tests for redirect + cache + tracking + stats E2E

  • Integration test for GET /:slug: known slug → 302 with the right Location; unknown → 404.
  • Test that a click is recorded when a redirect succeeds.
  • Test that a Redis outage doesn't break the redirect path (mock the cache to throw; expect a successful redirect).
  • Integration test for GET /links/:slug/stats: shape and counts are correct.
  • Playwright E2E: open dashboard → click a row → see the stats page render.
  • Add a GitHub Actions workflow that runs lint + type-check + tests on every PR.

Git Moment — required checks & protected branches

Once CI runs reliably, mark the checks "required" on main. PRs can no longer merge with a failing build. (Settings → Branches → Protected branches.)

Hints

  • Don't test implementation details. Test behaviour: "given input X, response is Y." Rewrites of the implementation should not break the tests.
  • Flaky tests destroy trust. If a test flakes, fix it or delete it; don't tolerate it.
  • Add a CI badge to each README. Easy 10-minute win.
  • Use a per-run test database (Docker container that's reset before each run) to keep tests deterministic.

Ship It — Deployment

Goal: a public URL anyone in the world can paste into a browser and use.

What is deployment?

Moving code from "runs on my laptop" to "runs on a computer somewhere everyone on the internet can reach." A platform takes your repo, builds it, runs it, and points a public URL at it. Push code → it redeploys.

What is a PaaS?

Platform-as-a-Service. You give them a Git repo; they handle the machines, the OS, the runtime. Vercel, Railway, Render, Fly are examples. Saves beginners weeks of YAML and infrastructure.

Production env vars vs local

Your local .env is local. In production, your hosting platform has its own UI to set environment variables. Audit every config used locally: DATABASE_URL, REDIS_URL, CORS_ORIGIN, NEXT_PUBLIC_API_URL, NODE_ENV, JWT_SECRET if any. Set them all.

Secrets — and the NEXT_PUBLIC_ trap

Anything prefixed NEXT_PUBLIC_ in Next.js ships to the browser. Never put secrets there. Anything else is server-only and safe. A common leak: putting an API key in a NEXT_PUBLIC_ var "just to make it work." Don't.

  • Run production migrations (prisma migrate deploy).
  • Smoke test the deployed health endpoint.

Dev B — Deploy frontend

  • Sign up for Vercel. Connect the web repo.
  • Set NEXT_PUBLIC_API_URL to the deployed backend URL.

  • Forgetting to run production migrations. The DB exists but is empty of tables.

Pull Request flow (rule for this project)

  1. Never push to main directly.
  2. Branch from up-to-date main with a name like feat/..., fix/..., chore/..., docs/....
  3. Commit small, commit often. Each commit message uses Conventional Commits: feat: add link form, fix: handle slug collision.
  4. Push. Open a PR. Title is what changed; description is why.
  5. The other dev reviews. Ask at least one question or leave at least one suggestion. Approve only after reading.
  6. Squash and merge. Delete the branch.

Conflicts

When two branches change the same lines, Git asks you to choose. Affected files contain <<<<<<< markers. Open them, pick which side wins (or merge by hand), remove the markers, git add, then continue with whatever Git's last message suggested. Don't panic. Don't git reset --hard in a panic. Ask your partner.

Recovery

  • git reflog — your time machine for "I lost a branch." Almost nothing is truly lost in Git.
  • git restore <file> — undo unstaged changes to a file.
  • git restore --staged <file> — unstage a file you accidentally staged.
  • git revert <commit> — make a new commit that undoes an old one. Safe on shared branches.

Conventional Commits — a small style

  • feat: a new feature
  • fix: a bug fix
  • chore: tooling, config, deps
  • docs: documentation only
  • refactor: internal change, no user-visible effect
  • test: tests only
  • style: formatting only (no code logic)

The contract your backend exposes — which URLs it responds to and what they accept/return.

Syntax for Promises. await pauses inside an async function until the Promise settles.

Appendix C — When You're Stuck

The 30-minute rule

If you've been stuck on the same problem for 30 minutes, you owe your partner a question — or at least a written note in a GitHub Issue. Stuck time multiplies fast when you're alone.

Stuck checklist

  1. Read the error message out loud. Every word. If you don't recognize one, search it.
  2. Did this work an hour ago? What's changed since? git diff tells you.
  3. Is it a real bug or a config thing? Wrong env var? Wrong port? Stale build?
  4. Have you actually restarted the dev server? Sometimes you haven't, even though you swear you did.
  5. Reduce the problem. Strip everything irrelevant until the bug is in the smallest piece of code that still breaks.
  6. Search the exact error string in quotes. Someone else hit this. Probably last week.
  7. Rubber-duck it. Explain the problem out loud, in full sentences. Halfway through, you'll often see the answer.
  8. Ask your partner. A specific question with "what I tried" beats "help, it's broken."

Communication norms

  • Daily check-in: yesterday, today, blockers. 10 minutes max.
  • One shared to-do list: GitHub Issues, tagged by phase.
  • Disagree in writing on PRs, not in heated voice calls. Async gives both of you time to think.
  • Celebrate small wins. Phase 4 working is a real moment.
  • If a checkbox sits unticked for > 2 days, that's a signal — talk about it.

What this plan deliberately leaves out (do NOT pre-build)

  • Authentication. Add in V2. It's a whole project on its own.
  • Microservices. The design diagram suggests separate services; for V1, run as a single NestJS app with multiple modules. Split later if you ever need to.
  • Custom domains. Vercel and Railway URLs are fine to start.
  • Rate limiting and abuse prevention. Worth adding once you have real traffic.
  • Dockerfiles for production. Use platform-as-a-service first; Dockerfiles later.
  • Monorepo tooling (Nx, Turborepo). Two repos is fine for V1.
